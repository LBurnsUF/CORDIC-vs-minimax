Computing sin/cos with No FPU

The Problem

Given an angle, return sin and cos using only add, subtract, shift, and an 8×8 hardware multiply.

Fixed-Point Representation

The Lookup Table

Precompute sin values, store in flash, interpolate between neighbors. Eats memory; interpolation still costs a multiply.

CORDIC

Rotate a vector toward the target angle using only shifts and adds. Each rotation angle has tan(α) = 2−i, so the multiply is a bit shift.

CORDIC iteration (rotation mode) xi+1 = xi − di · yi · 2−i yi+1 = yi + di · xi · 2−i zi+1 = zi − di · arctan(2−i) where di = sign(zi),   init: x0 = 1/K,   y0 = 0,   z0 = θ

The Gain Constant K

Each pseudo-rotation scales the vector by √(1 + 2−2i). The product K ≈ 1.647 is angle-independent. Pre-divide once, no per-iteration multiply.

K = ∏i=0n−1 √(1 + 2−2i)  ≈  1.64676 1/K  ≈  0.60725 K is constant for a given iteration count; computed once offline, applied as prescale to x0

Note: CORDIC eliminates the sine table but still needs a small atan(2−i) table (~FRAC_BITS entries).

Polynomial Approximation

sin(x) is an analytic function. Near any point, it equals its own Taylor series: an infinite sum of terms built from derivatives at that point. Truncate the series to a finite number of terms and you get a polynomial that approximates sin(x) over a limited interval.

Taylor series for sine sin(x) = x − x3/3! + x5/5! − x7/7! + …  =  ∑k=0∞ (−1)k x2k+1 / (2k+1)!
Taylor series for cosine cos(x) = 1 − x2/2! + x4/4! − x6/6! + …  =  ∑k=0∞ (−1)k x2k / (2k)!

Each additional term extends the interval of useful accuracy. The first term alone, sin(x) ≈ x, is good near zero. Adding the cubic correction captures curvature. Adding the fifth-degree term pushes the approximation further from the origin.

Argument Reduction

Polynomials approximate well only on a bounded interval. But angles span 0 to 2π. Argument reduction folds any angle into the first octant [0, π/4] using symmetry: sin(π − x) = sin(x), cos(π/2 − x) = sin(x), and so on. The polynomial only needs to be accurate on that narrow interval. Wider would require more terms.

Horner Evaluation

Evaluating x − x3/6 + x5/120 naively requires computing each power of x independently. Horner's method restructures the polynomial to nest multiplications. One multiply and one add per term, evaluated inside-out. Optimal for hardware with a fast multiplier.

Horner form (odd polynomial for sine, u = x²) sin(x) = x · (c0 + u · (c1 + u · (c2 + …))) n coefficients → n multiplies total (n−1 Horner steps + final x·r)

Convergence

Watch additional terms being added. Each term bends the polynomial closer to the true curve, starting from the center and extending outward.

Taylor vs. Minimax: Where the Error Goes

Taylor coefficients come from derivatives at the origin. The approximation is exact there and degrades toward the interval boundary. Minimax coefficients are computed by the Remez exchange algorithm to minimize the worst-case error across the entire interval. The result equioscillates: the error ripples uniformly rather than ramping up at the edges. For the same number of terms, minimax has a smaller worst-case error.

Taylor coefficients (from derivatives) ck = (−1)k / (2k+1)!  ⇒  c0 = 1,   c1 = −1/6,   c2 = 1/120,   c3 = −1/5040
Minimax coefficients (Remez exchange) minimize   maxx ∈ [0, π/4] | sin(x) − x · P(x²) | Equioscillation theorem: optimal P* has error that oscillates at equal magnitude across interval

Interpretation


  
What the Data Shows

  
Minimax polynomial evaluation is fastest at every width tested. CORDIC is competitive at 16-bit but falls behind at both extremes. Taylor trails minimax consistently due to extra terms for equivalent accuracy.

  
All three algorithms scale roughly quadratically with limb count, but the mechanisms differ. Polynomial cost is dominated by the fixed-point multiply, which grows as O(L2) on schoolbook hardware. CORDIC cost is the product of iteration count (linear in precision bits) and per-iteration shift-add cost (linear in limbs), also yielding near-quadratic growth but with a larger constant.

  
CORDIC accuracy plateaus at 4-5 LSB error across all widths, an inherent limitation of finite-iteration shift-add rounding. Both polynomial methods achieve ±1 LSB, limited only by the final fixed-point truncation.

        CORDIC
        No hardware multiplier. Shift and add are the only fast operations. Common on minimal FPGA softcores and older 4-bit/8-bit MCUs without MUL.
        On a chip with MUL, the iteration overhead exceeds the multiply cost it was designed to avoid. Accuracy limited to ~log2(iterations) bits.
      

      

        Taylor
        Prototyping or teaching. Coefficients are well-known and easy to derive. Reasonable when code clarity matters more than last-cycle performance.
        More terms than minimax for equivalent accuracy. At narrow widths the extra term is one more multiply; at wide widths, each multiply is expensive.
      

      

        Minimax
        Any chip with hardware MUL and a need for speed or accuracy. Fewest terms for a given error bound. Optimal for production fixed-point code.
        Coefficients are not closed-form; must be computed offline via Remez exchange. Harder to verify by hand than Taylor.
      

    
  


  
The Hardware Multiplier Changes Everything

  
CORDIC was invented for hardware that could only shift and add. The ATxmega128A1U has a single-cycle 8×8 hardware MUL. That one instruction makes polynomial evaluation viable and fast, negating CORDIC's core advantage. On a hypothetical xmega without MUL, every fixed-point multiply would become a shift-add loop, and the cost ranking would likely invert.

  
The scaling data confirms this: per-operation cost for polynomial terms (dominated by multiply) grows steeply with width, while CORDIC per-iteration cost (shift-add) grows more gently. At 8-bit where MUL is a single instruction, polynomials win easily. At 32-bit where MUL becomes multi-limb software, the gap between CORDIC and polynomial narrows, but CORDIC's 30-iteration count still makes it slowest overall.
